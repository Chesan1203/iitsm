# OOP concepts and design patterns (domain layer)

The domain layer (`app/domain/`) is pure business logic: it imports only the Python standard library, knows nothing about the web or the database, and never reads the clock itself. This is checked automatically by `tests/test_architecture.py`.

Python has no `interface` keyword and no truly private fields. We say so plainly and compensate: privacy is a naming convention (`_field`) backed by read-only properties and by tests, and interfaces are abstract base classes (`abc.ABC`) that cannot be instantiated.

## OOP concepts

**Encapsulation.** Every field is private (`_status`) and exposed through a read-only `@property`; there are no setters (the architecture test fails the build if a `@x.setter` appears in `app/domain/`). State changes only through behaviour methods such as `incident.acknowledge(actor, at)`, which check the rules before touching anything. The few internal mutators (`Incident._set`, `_add_note`, `_fire`) are underscore-prefixed, used only by the state classes, and `_set` accepts a whitelist of field names, all or nothing. Identity is write-once (`Entity.assign_id` refuses a second id). Value objects (`SlaTarget`, `Resolution`, `AuditRecord`, ...) are frozen dataclasses. Collections never leak: `Incident.notes` returns a copy and `Incident.snapshot()` copies the SLA tracker. Constructors validate and raise `InvalidInputError` with the offending field name. Limitation: Python cannot stop `inc._status = ...`; encapsulation here is a discipline that the tests and the layer rules enforce.

**Abstraction.** Callers use intention-revealing operations (`incident.resolve(...)`, `SlaCalculator.evaluate(incident, now)`, `DuplicateDetector.find_similar(...)`) and never see the lifecycle table, the clock arithmetic or the word-set maths behind them.

**Inheritance (only real "is-a").** `User` is specialised by `Employee`, `Technician`, `Administrator` and `SystemUser` (the automated actor). `Entity` is the common base of everything that has a database id (`User`, `ITService`, `Category`, `SlaPolicy`, `Incident`) and supplies the write-once id. `IncidentState` is specialised by `OpenState` and eight concrete state classes; `AssignmentStrategy` by three assignment strategies. Where "is-a" is false we do not inherit: `RuleBasedPriorityStrategy` has a `WeightedScorePriorityStrategy` (composition) instead of being one.

**Polymorphism.** The same call behaves differently depending on the object: `incident.close(...)` succeeds in `VerifiedState` and raises in `NewState`; any `AssignmentStrategy` or `PriorityStrategy` can be swapped at run time without the caller changing; `SystemTimeProvider` and `SimulatedTimeProvider` are interchangeable; any `IncidentObserver` can listen.

**Interfaces.** `IncidentObserver`, `PriorityStrategy` and `TimeProvider` are pure interfaces (every method abstract). `AssignmentStrategy` and `IncidentState` are abstract classes that add shared behaviour (see Template Method below). Trying to instantiate any of them raises `TypeError`, and tests assert it.

**Composition.** An `Incident` owns its `SlaTracker`, its list of `InvestigationNote`s, its `Resolution` and its `Feedback`: they have no meaning without it and are copied with it. A `SlaPolicy` owns its `SlaTarget`s; a `Technician` owns its skill set; `RuleBasedPriorityStrategy` owns its fallback strategy.

**Association and aggregation.** An `Incident` is associated with its reporter (`User`), its assigned `Technician`, its `ITService` and its `Category`: these objects live independently of any one incident. An `ITService` refers to its `SlaPolicy` only by id, which keeps the object graph shallow and persistence simple. `Incident` aggregates its observers: they are attached from outside, are not part of the incident's data and are not saved with it.

**Exception handling.** One hierarchy under `ITSMError` (15 classes, each with a human-readable `message`): `InvalidLoginError`, `UnauthorizedOperationError`, `InvalidStateTransitionError`, `TechnicianUnavailableError`, `WorkloadExceededError`, `NotFoundError` (with incident, service, category and user variants), `MissingSlaConfigurationError`, `DuplicateIncidentError`, `InvalidInputError` (carries the field name) and `PersistenceError`. Every action checks, in this order: is it legal in the current state (`InvalidStateTransitionError`), is this actor allowed (`UnauthorizedOperationError`), is the data valid (`InvalidInputError`, or the workload errors). That makes messages predictable and testable. A failing observer is contained: it is logged and the incident change stands.

**Collections.** `frozenset` for a technician's skills and for token sets; `dict` for SLA targets by priority, for the shared state objects by status and for the synonym map; `set` for the word sets of the duplicate detector (Jaccard needs set operations); `list` for notes and observers; `defaultdict` for grouping correlated incidents by service; `tuple` for the immutable notes of a snapshot; sorting with composite keys for tie-breaks (fewest incidents, then experience, then id); `MappingProxyType` for the default SLA targets so they cannot be altered.

## Design patterns

**State** (`app/domain/state/`). *Problem:* the lifecycle NEW, CLASSIFIED, ASSIGNED, ACKNOWLEDGED, IN_PROGRESS, RESOLVED, VERIFIED, CLOSED allows each action only in certain statuses and by certain people. In a single class this becomes an if/else chain repeated in every method. *Solution:* one class per status (`states.py`). `IncidentState` makes every action illegal by default, and each concrete state overrides only the actions legal there, so an illegal jump such as NEW to CLOSED cannot happen by construction. `Incident` holds no state object: each method asks `IncidentStateFactory.for_status(self._status)` for the shared, stateless state and delegates to it, so a restored incident works in any status. A table test checks that each state overrides exactly the actions in the lifecycle table of the plan, and a second test calls every other action in every state to prove it is rejected.

**Strategy** (`app/domain/strategies/`). *Problem:* the priority formula and the choice of technician are policies the organisation may want to change. *Solution:* `PriorityStrategy` (weighted score, rule based) and `AssignmentStrategy` (skill based, load based, weighted recommendation) hide each algorithm behind one interface. The service layer picks the active one by name, so switching needs no code change and no restart.

**Observer** (`app/domain/observer.py`, `events.py`). *Problem:* auditing and notifications must react to every change without the incident knowing who is listening. *Solution:* after each successful action `Incident._fire` builds an immutable `IncidentEvent` and passes it to every attached `IncidentObserver`, in order, after the change is complete. A failing observer is logged and skipped. The services layer plugs in an audit observer and a notification observer; adding a third listener needs no change to the domain.

Supporting idioms: **Template Method** (`AssignmentStrategy.select` is written once on top of each strategy's `rank`; `IncidentState._illegal` builds every rejection message), **Flyweight/Factory** (`IncidentStateFactory` hands out one shared instance per status), **Composition over inheritance** (`RuleBasedPriorityStrategy`). The Repository and Factory patterns for users belong to the persistence and services layers.
